## 1. Executive summary

Timbre Pronunciation Studio is a lightweight, local-first web application that lets developers and content creators define **reusable pronunciation rules** for names, brand terms, place names, acronyms and specialist vocabulary, then **hear the difference** in audio generated by Gnani AI's Timbre text-to-speech model.

The product is not a new TTS engine. It is a **workflow layer** on top of Timbre. It applies user-authored, pronunciation-friendly text substitutions to a script, sends the transformed text to Timbre, and keeps the original canonical script intact for display. The user hears both versions with identical model, voice, language and speed settings, and can save the rule set as a named dictionary to reuse across future scripts.

The strategic thesis is narrow and deliberately falsifiable:

> Gnani's public documentation offers a **support-gated** path to custom pronunciation (contact a point of contact), while competitors such as ElevenLabs offer a **self-service, reusable, developer-managed dictionary**. Timbre Pronunciation Studio demonstrates what a self-service equivalent would look like on top of the existing Timbre API.

Two things are explicitly **not** claimed: that Gnani lacks pronunciation capability, and that this application achieves native phoneme-level control. Both are addressed in §4.

## 2. Problem statement

### 2.1 The user problem

Text-to-speech systems mispronounce words whose spelling is not a reliable guide to their sound: invented brand names, Indian personal names in Latin script, place names, acronyms that should be read as words rather than letters, and specialist vocabulary.

For a developer shipping a voice product, this is not a cosmetic issue. A brand name mispronounced in every customer call, IVR prompt or notification is a recurring, visible defect. The manual workaround — editing the source text by hand — does not scale, is not reusable across scripts, and pollutes the stored content with spellings that were never meant to be displayed.

### 2.2 The specific gap this project targets

The following is the evidence base, stated precisely:

| # | Evidence | Source | Confidence |
|---|---|---|---|
| 1 | Gnani's text-normalisation guide states that if a brand or product name consistently misreads, "contact your Gnani point of contact — custom pronunciation entries can be added." | Gnani TTS Text Normalization Guide | As documented on 20 Oct 2026 |
| 2 | The public Timbre TTS REST request schema accepts exactly `text`, `model`, `voice`, `language`, `speed`, `audio_config`. There is no pronunciation dictionary, alias, phoneme, IPA, lexicon or SSML-phoneme parameter. | Gnani TTS Inference reference, OpenAPI spec | As documented on 20 Oct 2026 |
| 3 | Gnani's normalisation layer performs its own text substitution for pronunciation — e.g. the standalone word "Gnani" is rendered as "Gyaanee" in English, ज्ञानी in Hindi, ಜ್ಞಾನಿ in Kannada, and so on across nine languages. | Gnani TTS Text Normalization Guide | As documented on 20 Oct 2026 |
| 4 | Timbre v3.0 supports inline audio tags (`<laugh>`, `<whispers>`, `<pauses>`, and ten others). These control **delivery**, not pronunciation, and are stripped before synthesis on v2.5. | Gnani Audio Tags / Available Voices | As documented on 20 Oct 2026 |
| 5 | ElevenLabs documents reusable pronunciation dictionaries with alias and phoneme rules, dictionary reuse across requests, and API-level management. | ElevenLabs pronunciation dictionary docs | As documented on 20 Oct 2026 |

Evidence item 3 is the most important and is worth stating plainly: **Gnani already uses text substitution as its own pronunciation mechanism.** The application productises a mechanic the platform already relies on internally, and exposes it to developers as a managed, reusable, auditable workflow.

### 2.3 What this project does not claim

- It does not claim Gnani has no pronunciation capability. Item 1 proves otherwise.
- It does not claim the API can never support native phoneme control. The absence of a documented parameter is not proof of absence, and the API introduction page separately claims "SSML — Supported on TTS for fine-grained control". That claim was probed on 20 October 2026: the request returned HTTP 200 and audio, and listening to it on 22 October heard no tag at all — the markup is stripped, not spoken. It is therefore not a usable control (see §16.2 Q3).
- It does not claim an 8-of-8 listening result generalises to all voices, all languages, or all users.

## 3. Product vision

> A developer should be able to teach Timbre how to say their product's name once, save it, and never think about it again — and be able to prove the fix worked by listening to it.

The product's distinctive output is not audio. It is **a durable, portable, inspectable artefact** — a pronunciation dictionary — plus evidence that it works.

## 4. Evidence, assumptions and falsification

This section exists because the project rests on a hypothesis, and the PRD must state what would prove it wrong.

### 4.1 Proven

- Timbre v3.0 is reachable from the participant's account with audio tags working (verified in the Gnani TTS playground).
- The TTS REST endpoint and authentication scheme are documented, and were current as of 20 October 2026.
- The public request schema contains no pronunciation control parameter.

### 4.2 Assumed, not yet proven

| ID | Assumption | How it will be tested | If it fails |
|---|---|---|---|
| A1 | A user-authored respelling sent as `text` produces an audibly closer pronunciation for a meaningful share of terms | Milestone 3 POC, 8 curated terms, human listening | Gate B fails; project pauses and the user is informed before further build |
| A2 | Timbre's automatic text normalisation does not undo or mangle authored respellings | Inspect transformed text; verify by ear | Respellings must be authored to survive normalisation; POC design adjusts |
| A3 | Changing only the text (holding model, voice, language, speed fixed) isolates the pronunciation change | Controlled A/B pairs | Comparison is invalid; POC methodology is redesigned |
| A4 | Timbre v2.5 is usable with the same API key as v3.0 | One smoke-test call per model | MVP restricts model selector to the models actually entitled |
| A5 | The SSML claim in the API introduction does not translate into usable phoneme control | One controlled probe | If SSML works, the app gains a better mechanism and the demo improves; the alias path remains as fallback |

**Status, 22 October 2026:** every assumption above has now been tested. A1 passed (§11.1: 8 of 8 terms judged closer). A2 held — the adjusted audio speaks the respelling as spelled in 7 of 8 pairs, partly in 1, never not. A3 held by construction: every pair was generated with identical model, voice, language and speed. A4 held: `timbre-v2.5` answered with the same key. A5 failed in our favour — the SSML probe returned audio but the tag is stripped, so it gives no phoneme control.

### 4.3 Falsification criteria

The project is **not** built out if A1 fails, i.e. if fewer than 6 of 8 curated terms improve and surrounding words are damaged in a meaningful number of cases. In that event, the honest outcome is a documented negative result, not a shipped UI that does not work.

## 7. User stories and acceptance criteria

### US-01 — Create a dictionary

As a developer, I want to create a named dictionary so that rules for one product are kept separate from another's.

**Acceptance criteria**
- User can create a dictionary with a name; name must be non-empty and unique among existing dictionaries.
- Newly created dictionary becomes the active dictionary.
- Dictionary is persisted to disk immediately and survives an application restart.

### US-02 — Add a pronunciation rule

As a developer, I want to pair a written term with a pronunciation-friendly replacement so that Timbre says it my way.

**Acceptance criteria**
- A rule requires a non-empty source term and a non-empty replacement.
- Duplicate source terms within one dictionary are rejected with a clear message.
- Rule is saved and appears in the dictionary list with both source and replacement visible.
- Replacement text is validated against obvious hazards (e.g. contains angle brackets) with a warning, because normalisation strips inline markup.

### US-03 — Edit and delete rules

As a developer, I want to correct or remove a rule without recreating the dictionary.

**Acceptance criteria**
- Editing a rule updates it in place and persists immediately.
- Deleting a rule removes it and persists immediately.
- Deletion requires confirmation.

### US-04 — Apply rules to a script

As a developer, I want to paste a script and see exactly what will be sent to Timbre.

**Acceptance criteria**
- Original script remains visible and unmodified at all times.
- Transformed script is displayed separately.
- The UI states plainly that the transformed text is what is sent to the TTS engine.
- Rules apply only to whole-word/phrase occurrences (see §8).
- Applying rules is deterministic: the same script and dictionary always produce the same output.

### US-05 — See which rules fired

As a developer, I want to know which rules changed my text so that I can trust the result.

**Acceptance criteria**
- For each rule that matched, the UI shows the source term, the replacement, and the number of occurrences replaced.
- Rules that matched zero times are identifiable, so the user can spot a wrong spelling of the source term.

### US-06 — Generate original and adjusted audio

As a developer, I want to hear both versions with identical settings so that the comparison is fair.

**Acceptance criteria**
- Both generations use the same model, voice, language and speed within a single comparison.
- Both audio files are playable in the app.
- Generation only occurs on explicit user action; no synthesis on keystroke or on page load.
- If either call fails, the error is shown in plain language with the HTTP status, and the other result is not silently discarded.

### US-07 — Reuse a dictionary across scripts

As a developer, I want a saved dictionary to apply to a new script so that I do not re-enter rules.

**Acceptance criteria**
- Selecting a dictionary and pasting a new script applies existing rules without re-entry.
- Rules persist across application restarts.

### US-08 — Export a dictionary (stretch)

As a developer, I want the dictionary as a file so that I can version it or share it with my team.

**Acceptance criteria**
- Export produces a JSON file containing dictionary name, rules and metadata.
- Exported JSON is valid and re-importable in a later release (format is stable and documented in the Backend Schema).

### US-09 — Understand limitations

As a user, I want the tool to be honest about what it does.

**Acceptance criteria**
- A visible, non-dismissable-forever note states that this is an application-side text substitution workaround, not native phoneme control.
- The demo and README do not claim universal pronunciation correctness.

## 8. Rule-matching specification

This is the correctness core of the product. It is specified here because ambiguity here produces silent, hard-to-diagnose defects.

### 8.1 Matching semantics

| Property | Specification | Rationale |
|---|---|---|
| Unit | Whole word or whole phrase | Prevents `Ram` from corrupting `Ramachandran` or `Program` |
| Case | Case-insensitive for matching; replacement inserted verbatim | `Gnani`, `gnani`, `GNANI` should all be fixed by one rule; the user's chosen replacement casing is respected |
| Boundary | Word boundaries determined on Unicode word characters, with punctuation, whitespace and string ends as delimiters | Handles `Gnani's`, `(Gnani)`, `Gnani,` |
| Phrase support | Multi-word source terms allowed (e.g. `Gnani AI`) | Real brand terms are often two words |
| Priority | Longest source term first; ties broken by rule creation order | `Gnani AI` must win over `Gnani` at the same position |
| Overlap | No re-matching of already-substituted output | Prevents cascading substitutions |
| Idempotence | Applying the same dictionary twice to already-transformed text must not double-apply, **except** when one rule's replacement contains another rule's source: then the second pass matches again. The transform response emits `RULE_CHAIN_DETECTED` and `docs/LIMITATIONS.md` §1 states the exception. | Guards against accidental re-runs, and states the one case it cannot |
| Determinism | Same input + same dictionary ⇒ same output, always | Required for testing and for user trust |

### 8.2 Explicitly out of scope for matching

- Regex source terms.
- Substring/partial-word matching.
- Case-sensitive mode.
- Phoneme or IPA syntax in the replacement field (reserved, see §9.2).
- Language-specific morphological handling (e.g. Hindi case endings).

### 8.3 Worked examples

| Source rule | Input script | Result | Note |
|---|---|---|---|
| `Gnani` → `Gyaanee` | `Gnani AI makes voices.` | `Gyaanee AI makes voices.` | Simple whole word |
| `Gnani` → `Gyaanee` | `The Gnanis are here.` | unchanged | Plural not matched; whole-word rule only |
| `Gnani` → `Gyaanee` | `Gnani's demo` | `Gyaanee's demo` | Apostrophe treated as boundary |
| `Gnani` → `Gyaanee` and `Gnani AI` → `Gyaanee A I` | `Gnani AI` | `Gyaanee A I` | Longest match wins |
| `Timbre` → `Tamber` | `Timbre, timbre, TIMBRE` | `Tamber, Tamber, Tamber` | Case-insensitive matching |
| `Ram` → `Raam` | `Ramachandran` | unchanged | No substring matching |

## 13. Risks and mitigations

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | **Normalisation interference.** Timbre's TN pipeline rewrites text before synthesis and may alter authored respellings or spell out letter-like sequences. | High | High | Author respellings as plain lowercase words; inspect transformed text; test each POC term for survival; warn on markup characters |
| R2 | **Respelling fails to improve pronunciation.** Gate B fails. | Medium | Fatal | Run the POC before any UI work; stop and report rather than build around a broken premise |
| R3 | **SSML claim turns out true.** A native control exists, making the workaround look naive. | Low | High (upside) | One controlled probe during M3; if it works, add it as a second rule type and strengthen the demo |
| R4 | **Collateral damage to surrounding words.** A substitution degrades the sentence. | Medium | High | Whole-word matching; longest-first priority; per-term listening check on full sentences, not isolated words |
| R5 | **Docs drift.** Model versions, voices or parameters change during the build. | Medium | Medium | Re-verify against docs at M4 and before the demo; pin model and voice strings in one config location |
| R6 | **Credit exhaustion.** Repeated experimentation burns credits. | Low | Medium | Generate only on explicit action; session-level caching; short test scripts; monitor balance |
| R7 | **Scope creep** into multi-language, auth, or batch features. | High | Medium | §10 out-of-scope list; freeze date; stretch goals dropped first |
| R8 | **Deadline slip** from API troubleshooting. | Medium | High | Gates ordered so failures surface early; 6 Nov freeze leaves four days of buffer |
| R9 | **Weak public engagement** on the demo post, which affects shortlisting. | Medium | Medium | Lead with audible before/after, not architecture; keep the hook concrete ("Can you make AI say your name right?") |

## 15. Demo and submission strategy

### 15.1 Narrative

> "Every AI voice gets some names wrong. Here is how you teach Timbre yours — once — and prove it worked."

### 15.2 Demo sequence

1. Show the script with the term as normally written.

3. Show the rule: the term and its replacement, side by side.

- No claim of universal correctness.
- No claim that Gnani lacks pronunciation capability.
